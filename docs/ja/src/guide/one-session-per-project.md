# プロジェクトごとに1セッション

ztx はプロジェクトディレクトリごとにアクティブなセッションを1つに制限します。この制約により `ztx notify` が設定不要で動作します。プラグインフックと実行中のセッションの両方がプロジェクトルートから導出される単一のソケットパスを使用するため、配送は常にスキャンなしで O(1) で行われます。

## プロジェクトソケット

`ztx run` の起動時、ztx は正規化されたプロジェクトディレクトリから決定論的なソケットパスを計算し、そこに Unix ソケットをバインドします:

```
<runtime-dir>/<fnv1a-hash-of-cwd>.sock
```

ランタイムディレクトリは次の順序で解決されます:

1. `$ZTX_RUNTIME_DIR` (設定されていて空でない場合)
2. `$XDG_RUNTIME_DIR/ztx` (`$XDG_RUNTIME_DIR` が設定されている場合)
3. `$TMPDIR/ztx-run` (macOS のユーザーごとのデフォルト)

セッションと `ztx notify` の呼び出しはいずれも同じ正規化されたパス (シンボリックリンク解決済み) を FNV-1a 64ビットでハッシュするため、レジストリ検索なしに常に同じソケット名に到達します。

同ディレクトリの `<hash>.info` ファイルには、ラッパーの pid と作業ディレクトリが2行で記録されます。表示目的 (`ztx sessions`) と衝突報告にのみ使用され、ソケットの解決では読み込まれません。

## プロジェクトルート

ソケット名を決定するプロジェクトルートは次の通りです:

1. `ZED_WORKTREE_ROOT` 環境変数 — すべてのタスクとターミナルスレッドに対して Zed が設定します。
2. 現在の作業ディレクトリ — `ZED_WORKTREE_ROOT` が存在しないか空の場合に使用されます。

シンボリックリンクの違い (例: macOS の `/tmp` と `/private/tmp`) によって同一ディレクトリに別々のソケットが作成されないよう、パスはハッシュ化の前に正規化されます。

## 同じプロジェクトで2つ目のセッションを開始する

`ztx run` がプロジェクトソケットにすでにバインドされているライブセッションを検出した場合、既存のセッションを報告します:

```
a ztx session is already running in this project (/path/to/project)
  pid    12345
  socket /private/tmp/ztx-run/a3f8c2d1e4b56789.sock
  cwd    /path/to/project
```

インタラクティブに実行されている場合 (ターミナルに接続されている場合)、ztx は既存のセッションを終了して現在のターミナルで新しく開始するか確認を求めます。エディタの再起動によって孤立したセッション — プロセスはまだ待機しているが Zed のスレッドに接続されていない — を回収する際に便利です。

ztx は既存のラッパーに SIGTERM を送り、ソケットが解放されるまで最大2秒待ちます。猶予時間内にソケットがまだ使用中の場合、ztx は SIGKILL にエスカレートします。

所有者がすでに終了している古いソケットファイルは自動的に検出され (接続試行が失敗する)、確認なしに引き継がれます。

## セッションの一覧表示

```sh
ztx sessions
```

ランタイムディレクトリ内の `.sock` ファイルを現在所有しているすべてのセッションの pid、ソケットパス、作業ディレクトリを表示します。ソケットファイルが存在するものの所有者が終了しているセッションは、実行されていない状態として表示されます。

## 通知先の明示的な指定

単純な `ztx notify` はプロジェクトセッションにルーティングします。現在のディレクトリに関係なく特定のセッションを指定するには:

```sh
ztx notify --socket /private/tmp/ztx-run/a3f8c2d1e4b56789.sock --wake
```

複数のプロジェクトを同時に扱う場合に便利です。
