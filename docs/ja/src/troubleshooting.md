# トラブルシューティング

ztx は診断出力をターミナルに書き出しません。ラップ対象の CLI と同じターミナルを共有しているため、余分な出力があると子プロセスの画面が破損します。調査はすべて、帯域外の2つのツールに頼ります。

1. **ログファイル** — `ZTX_LOG=debug` を設定してすべてのサブシステム（画面状態の変化、タイトル発行、プレフィックスキーの操作、IPC インジェクション、エクスポート、ヒント候補数）のトレースを有効にします。ログは `ZTX_LOG_FILE` に追記されます。デフォルト値は `$XDG_STATE_HOME/ztx/ztx.log`（フォールバック先は `~/.local/state/ztx/ztx.log`）です。

   ```sh
   ZTX_LOG=debug ztx run -- claude
   ```

2. **ステートダンプ (state dump)** — `ctrl-] d` をいつでも押すと、ラッパーの内部状態のスナップショットを `$TMPDIR/ztx/state-<pid>-<n>.txt` に書き出します。ダンプには次の情報が含まれます: オルタネートスクリーン (alternate screen) がアクティブかどうか、子プロセスが最後に送信した OSC タイトル、キャプチャ済みスクロールバック (scrollback) の行数、オルタネートスクリーンの可視フレーム、直近のプライマリスクロールバック。ヒントモードは、ファイルパスの候補が見つからない場合にも自動でダンプを書き出します。

---

## セッション名が更新されない / 予期しない名前が表示される

**症状:** Zed のサイドバーに表示されるターミナルスレッドの名前が間違っている、古い値のまま、または現在のブランチや Agent CLI のステータスを反映していない。

**原因と対処:**

- **アダプターが一致しなかった。** `--adapter` を省略した場合、ztx は自動でアダプターを選択します。子プロセスのコマンド名が認識されなければ、タイトルモードはデフォルトの `passthrough` になります。この場合、子プロセス自身の OSC タイトルシーケンスがそのまま転送されます。自動検出が失敗した場合は `--adapter claude`（または `agy`）を明示的に指定してください。

- **`--title-mode passthrough` が明示的に設定されていた。** `passthrough` モードでは、ztx は子プロセスの OSC タイトルを変更せずに転送します。`managed` に変更するか、`--title-mode` を省略してアダプターに任せてください。

- **`--title-mode managed` を設定したが、セッション名が変わらない。** `managed` モードは子プロセスの OSC タイトルを抑制し、ztx 自身がタイトルを発行します。アダプターが意味のある名前を判断できない場合（例: ワークツリーのルートが解決できない場合）、タイトルが汎用的なものになることがあります。`ZTX_LOG=debug` で実行し、`title` を含むログ行を確認して、アダプターが何を発行しているか確認してください。

- **子 CLI が OSC タイトルをまったく発行していない。** `passthrough` モードと `prefix` モードでは、ztx は子プロセスがターミナルタイトルを設定することに依存しています。子プロセスが `OSC 0` または `OSC 2` シーケンスを発行しない場合、ztx に転送するものがありません。`ZTX_LOG=debug` で確認してください。タイトルシーケンスが処理されるたびに `title emissions` エントリが出力されます。

- **アダプターによる品質の違い。** Claude Code アダプターは、セッションタイトルをワークツリー（またはブランチ）名にステータス絵文字のプレフィックスを付けた形式（🔄 実行中、⏳ アイドル、🔔 入力待ち）で設定します。antigravity-cli アダプターは会話タイトルを公開します。アダプターが適用されない場合は、子プロセス自身のターミナルタイトルがそのまま通ります。したがって、セッション名の品質はどのアダプターが有効かによって異なります。

## `ctrl-] f`（ヒントモード）でファイルが見つからない

**症状:** `ctrl-] f` を押すと「no file paths found」のようなメッセージが表示される、または画面上に見えているパスにラベルがオーバーレイされない。

**ヒントモードの仕組み:**

- ラップ対象の CLI が **オルタネートスクリーン** モード（全画面 TUI）で動作している場合、ヒントモードは可視フレームをスキャンし、パスの位置に直接ラベルを描画します。可視フレームに認識できるパスが含まれていない場合は、後述のモーダルリスト方式にフォールスルーします。

- ラップ対象の CLI が **プライマリスクリーン** モード（スクロール出力）で動作している場合、ヒントモードはプライマリスクロールバックの直近 400 行とキャプチャ済みのオルタネートスクリーン行から構築されたモーダルリストを表示します。リストが空の場合は、ステートダンプが自動的に書き出されます。

**候補が見つからない理由:**

- ファイルパスがディスク上に存在しない（ztx は実在するファイルに解決できるパスにのみラベルを付けます）。
- パスがオルタネートスクリーンのアクティブ中にのみ表示され、その後更新されてしまった — オルタネートスクリーンの過去のコンテンツはスクロールバックにキャプチャされません。
- ワークツリーインデックスのスキャンが上限（エントリ数 20,000、深さ 8、`target`、`node_modules`、`vendor`、`dist`、`build`、`__pycache__`、および `.` で始まる隠しディレクトリをスキップ）に達した。

**自動ダンプの読み方:**

モーダル方式で候補が 0 件だった場合、ダンプのパスが画面に表示されます。ファイルを開いて次を確認してください。

- `alt_screen: true/false` — オルタネートスクリーンがアクティブだったかどうか。`true` で、かつインプレースオーバーレイが何も表示されなかった場合は、`ctrl-] f` を押した時点で可視フレームに認識できるパスがなかったことを意味します。
- `scrollback_lines` — キャプチャされたプライマリスクリーンの行数。0 は、子プロセスがオルタネートスクリーンモードのみで動作しており、プライマリスクロールバックに何も書き出されていないことを意味します。
- `## alternate screen (visible frame)` — ヒントモードが実行された時点で ztx が確認したコンテンツ。期待していたパスがこのセクションに含まれているか確認してください。
- `## primary scrollback` — プライマリスクリーンでキャプチャされた直近の出力。

## `ztx run` が起動しない / タイトルが更新されない

**症状:** `ztx run` が「このプロジェクトのソケットは既に別のセッションが保持している」と報告する、終了したはずのセッションが `ztx sessions` に表示される、またはプラグインフックのイベントで管理タイトルが反応しない。

**ソケットのルーティングの仕組み:**

`ztx run` と `ztx notify` はどちらも同じプロジェクトディレクトリを基準にします。具体的には、`ZED_WORKTREE_ROOT` が設定されている場合はその値（Zed がタスクに注入します）、設定されていない場合はプロセスのカレントディレクトリを使います。パスは正規化されたうえで FNV-1a でハッシュされ、ソケットディレクトリ（`ZTX_RUNTIME_DIR` → `$XDG_RUNTIME_DIR/ztx` → `$TMPDIR/ztx-run`）内の `<hash>.sock` が生成されます。レジストリはなく、両側が独立して同じパスを計算します。

**よくある原因:**

- **前のエディターセッションの残存セッション。** Zed を再起動した後も、ラッパープロセスが（閉じたターミナルに接続されたまま）動作し続けている場合があります。`ztx run` はこれを検出し、（インタラクティブに）古いセッションを終了してソケットを再バインドするか確認します。

- **古くなったソケットファイル。** 所有プロセスが終了したソケットファイルは、そのプロジェクトで次に `ztx run` が実行されたときに自動的に引き継がれます。

- **ディレクトリの不一致。** フックが報告する作業ディレクトリが（正規化後に）`ztx run` の起動ディレクトリと異なる場合、ハッシュが一致せず `ztx notify` は何も対象にしません。これは意図した挙動で、フックがエージェントを失敗させないための設計です。`ztx sessions` で実行中のセッションとその作業ディレクトリを確認してください。

  ```sh
  ztx sessions
  ```

## エクスポートの内容が欠けている、または予期しない内容になっている

**症状:** エクスポートされた Markdown が予想より短い、エージェントの応答が欠けている、または会話の途中で切れている。

**エクスポートソースの仕組み:**

- **ネイティブトランスクリプト (native transcript)（Claude Code アダプターのみ）。** Claude Code アダプターが `~/.claude/projects/` 以下にセッション JSONL を見つけた場合、エクスポートにはそのファイルが使用されます。これが最も忠実度の高いソースです。
- **フォールバック: ANSI 除去済み PTY キャプチャ。** ネイティブトランスクリプトが見つからない場合、エクスポートは ANSI エスケープシーケンスを除去した ztx 自身のスクロールバックキャプチャにフォールバックします。これは常に利用可能ですが、2 つの制限があります:
  - **オルタネートスクリーン** 上にのみ表示されたコンテンツ（全画面 TUI 内部のもの）はプライマリスクロールバックにキャプチャされないため、エクスポートには現れません。
  - キャプチャはリングバッファであり、非常に長いセッションでは初期の行が失われることがあります。

ネイティブトランスクリプト品質を期待しているにもかかわらず PTY キャプチャのような内容になっている場合は、`ZTX_LOG=debug` でトランスクリプトパスに言及するログ行を確認してください。Claude Code プラグインフックからの `ztx notify --from-hook` 呼び出しが、IPC 経由で正規のトランスクリプトパスを記録します。フックが発火していない場合、ztx はヒューリスティックな探索にフォールバックします。

## デスクトップ通知が表示されない

**症状:** Claude が完了したり入力を求めたりしても、システム通知が表示されない。

**要件と設定:**

- デスクトップ通知は **macOS のみ** に対応しています。他のプラットフォームでは通知パスはサイレントな no-op です。
- `terminal-notifier` ツールがインストールされ、`PATH` が通っている必要があります。ない場合はサイレントな no-op になります（`ZTX_LOG=debug` では `debug` レベルでログが出ます）。

  ```sh
  brew install terminal-notifier
  ```

- 通知は2つのイベントでのみ発火します: **入力待ち**（`Notification` フック）と **応答完了**（`Stop` フック）。その他のフックイベント（セッション開始、プロンプト送信など）では通知されません。
- `~/.config/ztx/config.toml` の `[notify]` セクションで `desktop = false` を設定すると、デスクトップ通知が完全に無効になります。

  ```toml
  [notify]
  desktop = false
  ```

- デフォルトの通知音は `"Glass"` です。サイレント通知にするには `sound = ""` を設定してください。

## 設定が反映されない

**症状:** `~/.config/ztx/config.toml` の設定が無視されているように見える。

**優先順位:** CLI 引数 > `config.toml` > 組み込みデフォルト。CLI フラグは常に最優先なので、コマンドラインで `--title-mode` や `--adapter` を渡している場合は、設定ファイルが上書きされます。

**エラー時のサイレントフォールバック。** ファイルが存在しない、読み込めない、または TOML が不正でも、ztx の起動は妨げられません。ファイル全体が解析できない場合は、すべての設定が組み込みデフォルトにフォールバックします。1 つのフィールドのみが不正な場合（例: 認識できないプレフィックス値）は、そのフィールドのみデフォルトにフォールバックし、残りのファイルは引き続き適用されます。

つまり、`config.toml` のタイポが意図しないデフォルト値をサイレントに復元することがあります。`ZTX_LOG=debug` で実行し、設定が読み込まれたかを確認してください。`no config loaded` または `ignoring malformed config.toml` のログ行は問題があることを示しています。

**設定ファイルのパス。** ファイルは `$XDG_CONFIG_HOME/ztx/config.toml`（フォールバック先は `~/.config/ztx/config.toml`）から読み込まれます。`XDG_CONFIG_HOME` も `HOME` も設定されていない場合、設定ファイルは読み込まれません。

**有効なプレフィックス形式。** `ctrl-<key>` または `c-<key>`（大文字小文字を問わない）のみ受け付けます（例: `ctrl-]`、`ctrl-a`、`C-]`）。`meta-x` や単体の `]` などの値はサイレントに無視され、デフォルトのプレフィックス（`ctrl-]`）が使用されます。`ctrl-@` はヌルバイトにマップされるため拒否されます。

## プレフィックスキーがラップ対象 CLI に届かない / ztx が誤って処理してしまう

**症状:** ラップ対象 CLI の内部で `ctrl-]` を押す（CLI 独自のキーバインドを使うために）と、代わりに ztx の操作がトリガーされる。

ztx のキーバインドはすべてプレフィックスキーの後ろに配置されているため、ラップ対象 CLI のキーマップは他のすべてのキーについて保持されます。唯一の例外がプレフィックスキー自体です: **プレフィックスキーを2回押す**と、リテラルのプレフィックスバイトが子プロセスに転送されます。例えばデフォルトのプレフィックス `ctrl-]` の場合:

```
ctrl-]  ctrl-]   →  リテラルの ctrl-] をラップ対象 CLI に送信
ctrl-]  f        →  ztx ヒントモードを開く
```

ラップ対象 CLI が `ctrl-]` のキーバインドを使用している場合は、`~/.config/ztx/config.toml` で ztx のプレフィックスを未使用のキーに変更してください:

```toml
prefix = "ctrl-\\"
```

## 既知の制限事項

- **セッション名の品質はアダプターに依存します。** Claude Code アダプターはワークツリー/ブランチ名とステータス絵文字を提供します。antigravity-cli アダプターは会話タイトルを公開します。アダプターがない場合は、子プロセス自身のターミナルタイトルのみが利用可能であり、その品質は CLI によって異なります。

- **Markdown エクスポートは、アダプターがネイティブトランスクリプト (native transcript) を見つけられない場合に PTY キャプチャにフォールバックします。** フォールバックでは、オルタネートスクリーン のコンテンツ（全画面 TUI 内部に表示されたもの）が除外されます。その旨を示す注記がエクスポートファイルに含まれます。

- **エクスポートは `$TMPDIR/ztx/` に書き出されます**（所有者のみのパーミッション、モード `0700`）。ztx は `run` 起動時に 7 日より古いエクスポートをベストエフォートで削除します。OS も定期的に一時ディレクトリを清掃するため、エクスポートは永続的な保存先ではありません。
